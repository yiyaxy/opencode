# M1 八万字长文转化提取计划

状态：**阶段一核心模板已实现，阶段二持久化骨架已实现，端到端链路待实现**。

## 1. 目标

以 30 分钟常规演讲稿或转写稿作为主要使用场景，以 8 万汉字作为极限批处理测试。系统应在日常场景优先保证响应速度和自动恢复能力，同时让最多 8 万汉字的纯文本或 Markdown 能够稳定完成摘要、字段提取、分类、改写或结构化转换。

- 不依赖模型一次性吞入全文，也不把长文永久塞进普通会话上下文。
- 不静默截断；原文的每个字符区间都有明确处理状态。
- 单段失败不导致整篇失败，支持自动重试、手动重试和应用重启后续跑。
- 已成功结果立即持久化，`partial` 响应能够保留并继续处理。
- 最终结果可追溯到原文段落或字符区间。
- 不在日志、错误上报或遥测中记录原文、提取结果和模型凭据。

“支持 8 万字”指端到端任务能力，不代表向模型发起单次 8 万字请求。即使模型声明支持 128K 或更大上下文，也必须走分块和持久化流程，为系统提示、工具定义、结构化结果和失败恢复保留空间。

常规性能基线按不超过 1 万汉字的单篇演讲转写稿定义，为 30 分钟演讲预留口速、停顿、标点和转写冗余。超过该基线仍正常处理，但自动切换到批处理策略，不承诺交互式完成时间。

## 2. 第一阶段范围

第一阶段支持：

- 直接粘贴文本。
- 本地 `.txt`、`.md` 文件。
- 用户选择已有或自定义输出模板，例如摘要、要点、实体、章节、问答或 JSON Schema。
- Desktop、Web 和 CLI 连接同一个服务器时查看同一任务状态和结果。

第一阶段不混入：

- PDF 扫描件 OCR、复杂 Word 排版、表格和图片理解；这些需要独立的文档解析层。
- 对 8 万字全文进行自由对话式推理；本能力聚焦可恢复的转换和提取。
- 多个文档之间的知识库检索；后续可复用本计划的切块、索引和引用能力。

## 3. 核心流程

```text
原文接收
  → 规范化与内容哈希
  → 按标题/段落切分
  → 按模型 Token 上限二次切块
  → 分块提取并即时保存
  → 结构校验与失败降级
  → 分层合并与去重
  → 最终格式化
  → 导出与来源追溯
```

### 3.1 原文接收

- 将原文作为独立任务资源保存，不复制进每一轮会话消息。
- 统一 UTF-8、换行符和不可见控制字符，但保留原始文本用于追溯。
- 计算内容哈希；同一原文、模板版本和模型策略可识别为同一任务输入。
- 记录字符数、字节数、估算 Token、标题层级和段落边界。
- 入口层明确显示预计分块数、所用模型和是否会把内容发送到外部 Provider。

### 3.2 自适应切块

- 优先按 Markdown 标题、空行、段落和句号切分，避免从句子中间截断。
- 使用模型目录中的上下文和输出限制按 Token 计算，不只按字符数切分。
- 第一版建议每块约 4K～8K 输入 Token，重叠 200～400 Token；最终值根据模型、模板和输出规模动态计算。
- 每块保存 `chunk_id`、顺序、原文起止位置、哈希和与前后块的重叠关系。
- 若 Provider 返回上下文超限，当前块自动二分后继续，不重跑已经成功的块。
- 8 万字任务不能因为模型上下文更大就退化成单次调用。

切块采用自动双档策略：

| 档位 | 自动适用范围 | 目标 Token | 最大 Token | 重叠 Token | 目标 |
| --- | --- | ---: | ---: | ---: | --- |
| 交互档 | 估算输入不超过 12K Token | 3K | 4K | 160 | 30 分钟演讲低延迟、快速首批结果和细粒度失败恢复 |
| 批处理档 | 估算输入超过 12K Token | 6K | 8K | 300 | 2 万至 8 万字吞吐、断点续跑和成本控制 |

用户不需要手动选择档位；调度器根据输入规模自动决定，并允许公司级配置覆盖。常规演讲稿通常拆为少量块并并发处理，单块失败只重试或二分该块。

### 3.3 分块提取

- 每次模型请求只承担一个明确动作，返回小而稳定的结果结构。
- 结果至少包含：块 ID、提取项、原文位置、警告、完成状态和 Schema 版本。
- 使用低随机性参数，输出上限根据模板预估并预留安全余量。
- 默认并发 2～4 个块，由 Provider 限流和本机资源动态调节，避免瞬时请求风暴。
- 每块使用幂等键，重复提交只能覆盖同一块的同一版本结果，不能产生重复数据。

### 3.4 校验与降级

每个块完成后立即执行：

1. 检查流是否正常结束，以及是否存在 `length`、`content-filter` 或 Provider 错误。
2. 校验 JSON 或用户模板结构，确认块 ID 和来源区间没有丢失。
3. 对格式错误优先执行“只修复格式”的小请求，不重新理解原文。
4. 对 `content_generation_failed` 且 `phase=extracting` 的响应保存部分结果，再重试当前块。
5. 对超时、连接中断、429 和可重试 5xx 最多自动重试两次并退避。
6. 对内容过滤、鉴权和无效配置停止自动重试，给出可操作提示。
7. 同一块连续失败后自动二分；仍失败则标记为待人工处理，不阻塞其他块。

### 3.5 分层合并

- 不把所有分块结果再次一次性提交给模型。
- 先按相邻 8～16 块形成中间结果，再逐层合并，直到得到最终结果。
- 对重复内容优先根据来源区间和稳定字段去重，模型语义去重只作为补充。
- 最终结果中的事实、摘要、实体或章节保留来源块和原文位置。
- 合并失败只重跑当前合并节点，不重跑底层提取。

## 4. 持久化与状态机

长文任务必须独立于普通会话执行，至少包含以下状态：

```text
pending → splitting → extracting → merging → completed
                         ↘ partial / failed / cancelled
```

建议数据实体：

- `content_job`：任务、原文哈希、模板、模型策略、总进度和最终状态。
- `content_chunk`：原文区间、Token 估算、重试次数、状态和错误分类。
- `content_result`：分块结果、中间合并结果、最终结果和 Schema 版本。

关键规则：

- 状态写入成功后再调度下一步，应用退出不会丢失进度。
- 服务启动时只恢复 `pending`、`extracting` 和 `merging` 中未完成的节点。
- 已完成块默认不重复调用模型；用户主动更换模型或模板时创建新版本。
- 取消任务要停止新请求，保留已完成结果，允许以后继续。
- 原文和结果保存周期必须可配置，并支持用户主动删除。

## 5. 错误处理与可观测性

当前原始 JSON 错误需要收敛为统一分类：

| 错误 | 自动动作 | 用户提示 |
| --- | --- | --- |
| 上下文超限 | 当前块二分 | 已缩小分块并继续 |
| `content_generation_failed` / `extracting` | 保存部分结果，重试当前块 | 提取阶段中断，进度已保留 |
| 输出达到长度上限 | 缩小块或增加输出预算 | 输出未完成，正在续提取 |
| JSON/Schema 不合法 | 仅执行格式修复 | 结果格式校验失败，正在修复 |
| 429、超时、可重试 5xx | 退避重试 | Provider 暂时不可用 |
| 内容过滤 | 停止当前块 | 当前段被 Provider 拒绝，需要人工处理或合规模型 |
| 鉴权、模型不存在 | 暂停整个任务 | 需要修复模型配置后继续 |

只记录任务 ID、块 ID、Provider、模型、HTTP 状态、请求 ID、耗时、Token、重试次数和错误分类。正文、提取结果、Authorization、API Key 和完整请求体禁止进入日志。

## 6. 产品体验

- 新增长文任务入口，不复用普通聊天输入框承载 8 万字正文。
- 展示总字符数、分块数、完成/失败数量、当前阶段和预计成本范围。
- 支持暂停、继续、取消、重试失败块和切换模型后重跑失败块。
- `partial` 状态允许预览和导出已完成结果，但必须标注缺失范围。
- 最终导出支持 Markdown、JSON 和用户选择的业务模板。
- Desktop、Web、CLI 只要连接同一服务器，就从服务端读取任务和进度；浏览器刷新不能丢任务。

## 7. 模块落位

遵循现有依赖方向，建议按以下层次实现：

- `packages/schema`：任务 ID、状态、模板和传输结构。
- `packages/core`：切块、任务状态机、持久化、重试、校验和分层合并。
- `packages/llm`：复用现有协议适配器和统一错误事件，不在长文模块重复实现 Provider。
- `packages/protocol`：长文任务创建、查询、取消、继续和结果读取协议。
- `packages/server`：HttpApi 处理与任务调度入口。
- `packages/app`：长文任务创建页、进度页、部分结果和导出界面。
- `packages/opencode`：在需要兼容旧会话入口时只做适配，不建立第二套任务事实源。

若公开 Protocol 或 Server `HttpApi` 发生变化，必须从 `packages/client` 运行 `bun run generate`，不得直接修改生成目录。

## 8. 配置边界

第一版应提供服务器级配置，默认值仅作为安全起点：

- 单任务最大字符数：80,000。
- 交互档单块目标/上限输入 Token：3K/4K，重叠 160 Token。
- 批处理档单块目标/上限输入 Token：6K/8K，重叠 300 Token。
- 并发数：2～4。
- 单块自动重试：2 次。
- 任务超时按块和阶段控制，不能给整篇设置一个短总超时。
- 原文和结果保存周期：由公司数据策略确定。
- Provider 白名单：由公司模型网关策略确定。

配置中只保存策略和地址引用，不保存真实密钥。浏览器不能直接持有 Provider 凭据。

### 8.1 常规演讲性能与稳定性指标

在公司指定参考模型、稳定网关和不超过 1 万汉字的输入条件下，发布验收目标为：

- 本地规范化、切块和任务入库 P95 不超过 500 毫秒，首批模型请求在 1 秒内开始调度。
- 首个有效分块结果 P95 不超过 15 秒，完整提取 P95 不超过 90 秒；具体参考模型与硬件必须随发布版本固化。
- 任一分块出现一次超时、429、可重试 5xx 或 `content_generation_failed` 时，任务能够自动恢复，不要求用户重新提交全文。
- 原文覆盖率、结果状态可见率和已完成块恢复率均为 100%，不允许静默截断或因刷新页面丢失进度。
- Provider 持续不可用时允许超过时间目标，但必须在 3 秒内展示可理解的降级状态，并保留已完成结果。

速度指标不能只通过放大单块实现；需要结合小批量并发、结果即时保存、Schema 校验和失败块独立重试。外部 Provider 延迟不在本地绝对控制范围内，因此产品保证的是参考环境下的验收指标，以及任何环境下的进度保留和明确降级。

## 9. 实施阶段

### 阶段一：核心模板

- 已定义任务、分块、结果和错误分类 Schema（`packages/schema`）。
- 已实现文本规范化、结构化切块、Token 预算、来源区间和块状态模板（`packages/core`）。
- 已实现与 `content_generation_failed`、上下文超限、限流、超时和格式错误对应的统一失败分类与动作建议。
- 实现单块提取、结果校验、失败二分和分层合并。
- 使用现有 Provider/模型配置，不新增生产依赖。

当前进度：核心切块模板已改为自动双档。常规输入默认使用 3K/4K/160 Token 的交互档，超过 12K Token 自动使用 6K/8K/300 Token 的批处理档；8 万汉字样本可生成 14 个连续覆盖块。阶段二已增加 `content_job`、`content_chunk`、`content_result` 表和存储接口，支持幂等写入与运行中块恢复；真实 Provider 调度、单块提取、分层合并和端到端时间指标仍待后续实现。

退出条件：命令行或内部接口可以处理 8 万字样本，并输出完整的分块结果及来源区间。

### 阶段二：持久化与恢复

- 已增加任务、分块和结果持久化表及迁移。
- 已增加 `ContentExtractionStore`，支持任务创建、来源读取、分块查询、分块状态保存、结果幂等保存和运行中块恢复为待处理状态。
- 实现幂等调度、进程重启恢复、暂停、继续和取消。
- 对部分响应和失败块提供独立恢复路径。

退出条件：任务处理中强制退出服务，重启后能从未完成块继续，不重复已完成调用；当前存储骨架已具备，调度恢复和暂停/继续仍未完成。

### 阶段三：产品界面

- 增加创建、进度、结果、错误处理和导出界面。
- 打通 Desktop、Web、CLI 连接同一服务器的状态共享。
- 增加外部 Provider 数据发送提示和成本提示。

退出条件：用户无需查看日志即可完成创建、等待、处理失败、继续和导出。

### 阶段四：集中测试与发布验证

功能模板完成后再进入集中测试，不在前三阶段批量新增测试。

- 使用 2 千、2 万、5 万和 8 万汉字样本验证完整覆盖。
- 以不超过 1 万汉字的 30 分钟演讲样本单独统计 P50/P95 首结果时间、完成时间、重试率和成功率。
- 验证 Markdown 多级标题、超长单段、混合中英文和代码块。
- 验证中途断网、429、5xx、流中断、格式错误、应用退出和手动取消。
- 验证结果来源区间覆盖原文且无静默缺块。
- 验证日志和错误上报不包含原文、结果和凭据。

## 10. 验收标准

8 万字能力达到可用必须同时满足：

1. 原文字符区间覆盖率为 100%，每个区间处于已完成、明确失败或用户排除状态。
2. 稳定 Provider 下，单块临时失败不会导致整篇任务失败。
3. 进程或应用重启后可继续，已完成块不会重复收费。
4. 没有静默截断；部分完成时可以看到缺失块和原因。
5. 最终结果可以定位到对应的原文块和字符区间。
6. 普通聊天会话不会因为 8 万字任务迅速触发上下文压缩或溢出。
7. Desktop、Web、CLI 连接同一服务器时看到一致的任务进度和结果。
8. 日志、遥测和错误信息不包含正文、提取结果或密钥。

## 11. 推荐顺序

先实现“切块、持久化、单块重试、分层合并”这条可靠主线，再扩展 PDF/Word、知识库和多 Agent。首版不通过无限增大上下文、超时或重试次数伪装可靠性，也不把会话压缩摘要当作长文提取结果。
